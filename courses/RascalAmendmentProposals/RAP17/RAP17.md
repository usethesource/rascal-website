## Abstract

The topic of RAP 16 (Error Tree Support) was how handle regular code that tries to access parts of error trees that are not present ("beyond the dot"). This RAP
builds on this by adding support for better handling of ambiguous trees.

## Motivation

For a "real world" issue and caused by lack of support for ambiguous trees and discussion see: https://github.com/usethesource/rascal/issues/2579

Currently when code tries to access part of a tree but the tree is ambiguous, the interpreter throws a static error as if the error was
caused by a compile time error, for example:
```
import ParseTree;
import vis::Text;
import IO;

syntax S = O? A a | A a; 
syntax A = "a";
syntax O = "o"?;
...
S s = parse(#S, "a", allowAmbiguity=true);
rascal>println(prettyTree(s));
 ❖
 ├─ S = A a 
 │  └─ A = "a"
 └─ S = O?  A a
    ├─ ❖
    │  ├─ O?
    │  └─ O?
    │     └─ O = "o"?
    │        └─ "o"?
    └─ A = "a"

ok
rascal>println("a: <s.a>");
|prompt:///|(13,1,<1,13>,<1,14>): Undeclared field: a for Tree
Advice: |https://www.rascal-mpl.org/docs/Rascal/Errors/CompileTimeErrors/UndeclaredField|
```

But the underlying cause is actually a dynamic error: the tree happens to be an ambiguous tree so accessing a field does not make sense.
Because static errors cannot be caught, there is no way for a developer to handle this situation without explicitly checking beforehand
if a tree is an ambigous tree.

## How to handle attempts at accessing subtrees of ambiguous trees

There are a limited number of ways code can try to access or analyze subtrees of parse trees (not counting Tree level access, then you are on your own):

- Checking if a field exists (`tree has name`, `tree.name?`)
- Checking if a tree is generated by a certain labeled production (tree is label)
- Named field access (`tree.field`, `tree.name?alt`)
- Named field assignment (`tree.field=subtree`)
- Indexed field access (`tree[index]`)
- Indexed field assignment (`tree[index] = subtree`)
- Matching using concrete syntax `((Stat)\`if \<Expr e\> then \<StatList s\>\`)`


### Checking for field existence

Field existance checks on an ambiguous tree should always return `false`.

### Checking if a tree is generated by a labeled production

This should also return `false` when performed on an ambigous tree: the children of an ambiguous tree can be of different productions so there is no one labeled production.

### Named field access and assignment

There is no sensible way to implement this so throwing an exception is the only solution.

We already solved an almost identical problem (access to non-existing subtrees) when working with error trees in RAP16. In that case the top-level node would be an `error` node and access could fail if a subtree "after the dot" was accessed.
In that case a special `ParseErrorRecovery` exception was thrown when such an access was attempted. This allows the programmer to catch such exceptions at the level of abstraction where they can be handled instead of having to sprinkle the code with checks for error trees.

We propose to use the same approach here: throw the same `ParseErrorRecovery` exception when access to a field of a parse tree fails because the parse tree is ambiguous.

### Indexed field access and assignment

Accessing an indexed field on an ambiguous tree should throw a `ParseErrorRecovery` exception.

### Matching using concrete syntax

This already works "out-of-the-box": matching fails on ambiguous trees but typed holes can match ambiguous trees.
We do not have a way to explicitly match ambiguous trees.

**Conclusion:**

- `has` should fail on ambiguous trees.
- `is` should fail on ambiguous trees.
- `tree.name?alt` should return alt when tree is ambiguous.
- Named field access on ambiguous trees should throw an exception.
- Indexed field access on ambiguous trees should throw an exception.

## Handle faulty access to ambiguous trees in backtracking contexts and generators

Analogous to what whas discussed in RAP16, exception caused by ambiguous tree access should be propagated normally during backtracking and in generators.

## Compatibility

This proposal is backwards compatible in the sense that if code used to work without throwing static errors, it will continue to function but now throws a dynamic error.
Try/catch blocks that happen to catch all exceptions (or already catch `ParseErrorRecovery` exceptions will now also catch exceptions when caused by access to an ambiguous tree.

## Implementation

We can follow exactly the same implementation path we did for the error recovery case. Start by writing tests and then add support to both the interpreter and compiler. Note that the implementation should be simpler for ambiguous trees than for error trees: for ambiguous trees all field access should result in a `ParseErrorRecovery` exception while for error trees only access to fields "after the dot" should fail.

## Alternatives considered

### Special handling of ambiguities on similar trees
What if all alternatives do have a particular field? We could let field checks succeed in that case as that seems sound. But in practice we foresee this would cause confusion, because although all alternatives have a particular field, it is unclear which one to return on access so field access would still throw an exception.
The same goes for ambiguities where all alternatives are generated by the same (labeled) production. Letting `tree is label` succeed will cause trouble later.

### Use of different exceptions for faulty field access on error trees and ambiguous trees
Error recovery often causes ambiguities even when the syntax does not normally allow ambigous trees. Separation between true ambiguities and ambiguities caused by
error recovery can be done by checking the alternatives of an ambiguous tree for error subtrees.
In practice we expect most ambiguities to be caused by error recovery so throwing only `ParseErrorRecovery` exceptions seems to offer the easiest path for developers.
